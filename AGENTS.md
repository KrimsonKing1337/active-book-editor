# ActiveBook editor: локальные правила

## 7. React и JSX

### 7.1. Общие принципы

Компоненты должны преимущественно отвечать за:

- Получение необходимых данных
- Подготовку данных для отображения
- Обработку пользовательских событий
- Рендеринг интерфейса

Сложную независимую логику выносить за пределы компонентов.

Не перегружать JSX вычислениями и преобразованиями данных.

**Respect API boundaries and React lifecycle.** Represent absence according to the receiving contract: domain data, controlled input, CSS, component or hook. Keep valid `null`/`undefined` inputs and controlled empty strings. Do not change mounting, state, hook order or side effects for cosmetic simplification; follow the Rules of Hooks and prevent numeric visibility guards from accidentally rendering zero.

### 7.2. Вычисления перед JSX

Вычислять производные значения, подписи, описания и другую логику отображения перед `return`.

**Нежелательно:**

```tsx
<button>
  {isProjectBusy ? 'Подождите...' : 'Сохранить'}
</button>
```

**Предпочтительно:**

```tsx
const projectBusyStatusLabel = isProjectBusy
  ? 'Подождите...'
  : 'Сохранить';

return (
  <button>
    {projectBusyStatusLabel}
  </button>
);
```

Простые значения можно использовать непосредственно в JSX.

Не создавать промежуточные переменные для очевидных обращений к уже подготовленным данным.

### 7.3. Деструктуризация перед JSX

Если в JSX используется больше двух свойств одного объекта, предпочитать предварительную деструктуризацию.

```tsx
components.map((componentCur) => {
  const {
    id,
    description,
    packageName,
    name,
    title,
  } = componentCur;

  return (
    <button
      key={id}
      type="button"
      title={description}
      onClick={() => onInsertCustomComponent(packageName, name)}
    >
      Добавить {title}
    </button>
  );
});
```

Если используется не больше двух свойств, деструктуризация необязательна.

Не выполнять избыточную деструктуризацию, если она ухудшает понимание кода.

### 7.4. Обработчики событий

Объявлять многострочные или сложные обработчики отдельно перед JSX.

**Неправильно:**

```jsx
onDelete={(name) => {
  setProperty(name, undefined);
  commitStyle();
}}
```

**Правильно:**

```tsx
const handleDelete = (name: string) => {
  setProperty(name, undefined);
  commitStyle();
};

return (
  <Properties
    onDelete={handleDelete}
  />
);
```

Если обработчик уже имеет подходящую сигнатуру, передавать его напрямую.

```tsx
onDelete={handleDelete}
```

Не создавать промежуточную стрелочную функцию без необходимости.

Короткие однострочные обработчики допустимы, если они остаются понятными и не содержат сложной логики.

### 7.5. Расположение обработчиков в пропсах

Пропсы обработчиков событий (`onClick`, `onChange`, `onFocus` и другие) размещать в конце списка.

Если обработчиков больше двух, отделять их от остальных пропсов пустой строкой.

Правило распространяется на:

- JSX-пропсы
- Деструктуризацию пропсов
- Типы и интерфейсы пропсов

```tsx
export const Images = ({
  images,
  canImport,

  onChange,
  onImportAsset,
  onDelete,
}: BackgroundImagesProps) => {
  // ...
};
```

### 7.6. Форматирование JSX

Если элемент содержит `children`, открывающий тег, содержимое и закрывающий тег располагать на отдельных строках.

**Неправильно:**

```tsx
<span>Название эффекта</span>
```

**Правильно:**

```tsx
<span>
  Название эффекта
</span>
```

Исключения допустимы, если переносы могут нарушить пробелы или отображение смешанного текстового содержимого.

Соседние JSX-элементы предпочтительно отделять пустой строкой.

Это относится и к ситуациям, когда однострочный элемент соседствует с многострочным.

Не вставлять пустые строки механически, если элементы образуют единую тесно связанную конструкцию и разделение ухудшает читаемость.

### 7.7. Условный рендеринг

Не использовать однострочные конструкции с `&&` для рендеринга компонентов.

**Нежелательно:**

```tsx
{showBackgrounds && <BackgroundInstances project={project} />}
```

**Правильно:**

```tsx
{showBackgrounds && (
  <BackgroundInstances project={project} />
)}
```

Сложные условия вычислять перед `return`.

Учитывать, что числовые и строковые значения в условиях React могут приводить к неожиданному отображению.

### 7.8. Зависимости React-хуков

В массивах зависимостей сначала указывать значения данных, затем функции.

```ts
useEffect(() => {
  updatePreview();
}, [effectId, options, updatePreview]);
```

Не удалять необходимые зависимости ради устранения предупреждений ESLint.

Не изменять семантику эффектов при перестановке или рефакторинге зависимостей.

### 7.9. Ref

Проект использует React 19.

- Не использовать `forwardRef` в новом коде
- Передавать `ref` как обычный prop
- При рефакторинге существующих компонентов использовать механизм React 19
- Проверять корректность типизации и передачи `ref`

Если код должен быть совместим с React 18, учитывать особенности старой модели передачи `ref` и не удалять `forwardRef` механически.

## 8. CSS и classnames

Для объединения и условного применения CSS-классов использовать исключительно библиотеку `classnames`.

Не использовать для формирования `className`:

- Тернарные операторы
- Конкатенацию строк
- Шаблонные литералы
- Массивы с `.join()`
- Самостоятельные функции объединения классов

**Неправильно:**

```tsx
className={colorDisabledReason ? styles.DisabledColors : styles.Colors}
```

```tsx
className={`${styles.Select} ${layoutStyles.Unit}`}
```

```ts
const classes = [styles.Button, variantClass, className]
  .filter(Boolean)
  .join(' ');
```

**Правильно:**

```ts
const editorScreenClassNames = classNames({
  [styles.EditorScreen]: true,
  [styles.isStructureVisible]: showStructure,
  [styles.isNarrativeHidden]: !showNarrative,
});
```

Одиночный статический класс передавать напрямую.

```tsx
className={styles.Button}
```

Не создавать промежуточные переменные для одиночного статического класса без необходимости.

## 9. Структура проекта и декомпозиция

### 9.1. Организация компонентов

**Один React-компонент — одна директория.**

- Каждый компонент размещать в отдельной директории
- Использовать `index.ts` для публичного экспорта
- Не размещать несколько самостоятельных компонентов в одном файле
- Использовать существующие соглашения об именовании файлов и директорий
- Не объединять независимые компоненты исключительно ради уменьшения количества файлов

Исключения из этого правила допускаются только по явному согласованию.

### 9.2. Разделение ответственности

Выносить сложную логику из компонентов в соответствующие модули.

Для организации использовать при необходимости:

- `components/` — вложенные компоненты
- `hooks/` — React-хуки
- `utils/` — вспомогательные функции
- `@types.ts` — связанные типы
- `index.ts` — публичные экспорты

Чистые функции, не зависящие от React, предпочтительно размещать в `utils`.

Повторяющуюся логику React выносить в собственные хуки.

Использовать `index.ts` для формирования понятного публичного интерфейса модуля.

### 9.3. Размер модулей

Если файл становится слишком большим или объединяет несколько разных обязанностей, разделять его на логические части.

Не создавать дополнительные уровни вложенности без необходимости.

Ориентироваться на:

- Ответственность модуля
- Повторное использование
- Удобство навигации
- Простоту тестирования
- Читаемость

Не дробить небольшие функции на множество файлов без практической пользы.

## 10. Тексты пользовательского интерфейса

Эти правила относятся к текстам, которые видит пользователь ActiveBook.

### 10.1. Обращение к пользователю

Использовать вежливое обращение на «Вы».

Не переходить на «ты» в интерфейсных сообщениях.

### 10.2. Пунктуация

Не ставить точку в конце последнего или единственного предложения интерфейсного текста.

**Нежелательно:**

```ts
const message = 'Проект успешно сохранён.';
```

**Правильно:**

```ts
const message = 'Проект успешно сохранён';
```

Если текст состоит из нескольких предложений, сохранять необходимые знаки препинания между ними.

Вопросительные, восклицательные знаки и другие смысловые знаки пунктуации сохранять.

### 10.3. Кавычки

В русскоязычных текстах интерфейса использовать кавычки-лапки `"..."`, а не кавычки-ёлочки `«...»`.

Правило не относится к синтаксису строк TypeScript, JSON и другим техническим конструкциям.

### 10.4. Область применения

Правила интерфейсной пунктуации и обращения не распространяются автоматически на:

- Документацию
- Комментарии в коде
- Технические сообщения консоли
- Тексты исключений
- Внешние данные

В этих случаях использовать оформление, соответствующее контексту.


## Проверки и локальная разработка

Быстрые проверки: `npm run typecheck`, `npm run typecheck:test`, `npm run lint:ts:check`, `npm run lint:css:check`, `npm run test:unit`, `npm run test:component`, `npm run test:scripts`.
Браузерные проверки запускайте отдельно через `npm run test:browser`.
Конфигурации сборки, тестов, алиасы и workspaces относятся к этому репозиторию.
`npm run make` в core сам повышает версию и создаёт архив. Для обновления зависимости редактора используйте `npm run core:package`; ожидаются изменения manifest/lock обоих репозиториев.
