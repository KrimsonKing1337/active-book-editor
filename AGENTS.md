# ActiveBook — правила разработки

## 1. Общие принципы

Главный принцип — **код должен быть простым, последовательным и понятным при чтении сверху вниз**.

- Предпочитать небольшие, логически завершённые операции сложным выражениям
- Не сокращать код ради сокращения количества строк
- Разделять сложную логику на простые действия с осмысленными названиями
- Не создавать дополнительные переменные или функции, если они не улучшают читаемость
- Избегать избыточных абстракций и усложнения архитектуры
- Соблюдать существующие соглашения проекта
- Не изменять код, не относящийся к текущей задаче
- При сомнениях выбирать наиболее простую и понятную реализацию

**Корректность работы программы и сохранение существующего поведения обязательны. Читаемость имеет приоритет перед необязательными стилистическими предпочтениями.**

Если какое-либо правило ухудшает читаемость или противоречит другому требованию, не применять его механически.

## 2. ESLint и форматирование

### 2.1. ESLint

- Использовать конфигурацию ESLint соответствующего пакета
- Не дублировать в этом документе правила, уже реализованные через ESLint
- Не отключать правила ESLint ради обхода ошибок без обоснованной необходимости
- После изменений проверять затронутый код ESLint
- Не исправлять существующие предупреждения в несвязанных с задачей файлах

Если требования ESLint противоречат читаемости, сообщить о проблеме, а не обходить проверку самостоятельно.

### 2.2. Существующее форматирование

- Не изменять существующее форматирование без необходимости
- Придерживаться принятого в файле стиля
- Применять правила форматирования преимущественно к новому или изменяемому коду
- Не выполнять массовое форматирование несвязанных участков
- По возможности ограничивать длину строк TypeScript 120 символами

### 2.3. Импорты

Импорты типов размещать перед остальными импортами.

Если из одного модуля импортируется больше трёх типов, использовать отдельный `import type`.

**Неправильно:**

```ts
import {
  type ChangeEvent,
  type ClipboardEvent,
  type CSSProperties,
  type KeyboardEvent,
  useEffect,
  useRef,
  useState,
} from 'react';
```

**Правильно:**

```ts
import type {
  ChangeEvent,
  ClipboardEvent,
  CSSProperties,
  KeyboardEvent,
} from 'react';

import {
  useEffect,
  useRef,
  useState,
} from 'react';
```

Дополнительные требования:

- При превышении 100 символов в инструкции импорта переносить элементы на отдельные строки
- При смешанном импорте сначала указывать типы, затем остальные значения
- Не разбивать короткие импорты без необходимости
- Не создавать повторные импорты из одного модуля без причины

## 3. Именование

### 3.1. Переменные и функции

Имена должны отражать назначение, а не только технический тип значения.

Предпочитать осмысленные названия:

- `previewStyle` вместо `value`
- `currentLayerCount` вместо `count`, если без контекста назначение неочевидно
- `resolvedOptions` вместо `data`
- `isRegistered` вместо `flag`

Не использовать абстрактные имена без необходимости.

Не переименовывать существующие сущности, если новое имя не улучшает понимание кода.

### 3.2. Булевы переменные

Предпочитать префиксы:

- `is` — состояние
- `has` — наличие
- `can` — возможность
- `should` — необходимость действия
- `show` — отображение

Например:

```ts
const hasOptions = options.length > 0;
const canRender = isReady && hasOptions;
const shouldUpdate = currentVersion !== nextVersion;
```

### 3.3. Переменные в итерациях

Для многострочных операций использовать суффикс `Cur`.

```ts
components.map((componentCur) => {
  return componentCur.name.toLowerCase();
});
```

Для однострочных операций использовать `cur`, если значение понятно из контекста.

```ts
components.map((cur) => cur.option);
```

### 3.4. Аргументы обработчиков

- Для единственного объекта события допустимо имя `e`
- Для единственного переданного значения допустимо имя `val`
- Если аргументов несколько или краткое имя затрудняет понимание, использовать осмысленные названия
- Не использовать сокращения, смысл которых невозможно понять из контекста

### 3.5. Обработчики событий

Предпочтительный формат — префикс `handle`.

```ts
const handleClick = () => {};
const handleChange = (val: string) => {};
const handleDelete = () => {};
```

Существующий вариант с суффиксом `Handler` допустим:

```ts
const deleteHandler = () => {};
```

Не переименовывать работающий код исключительно ради унификации.

Функции, выполняющие действие, не называть `watch`, если они непосредственно ничего не отслеживают.

## 4. TypeScript и типизация

### 4.1. Вложенные типы

Выносить содержательные вложенные объектные структуры в отдельные именованные типы.

**Не рекомендуется:**

```ts
type BackgroundEffect = {
  id: string;
  images?: {
    src: string;
    style?: CSSProperties;
  }[];
};
```

**Предпочтительно:**

```ts
type BackgroundEffectImage = {
  src: string;
  style?: CSSProperties;
};

type BackgroundEffect = {
  id: string;
  images?: BackgroundEffectImage[];
};
```

Не создавать дополнительные типы для примитивных или тривиальных конструкций, если это ухудшает понимание.

### 4.2. Проверки типов

При работе с `unknown` сначала сужать тип, затем обращаться к свойствам.

Использовать:

- `typeof`
- `Array.isArray`
- `in`
- существующие type guards
- собственные функции проверки типов, когда это оправданно

Не применять `as` исключительно для подавления ошибок TypeScript.

Type assertion допустим, если корректность типа обоснована и безопасное сужение невозможно либо нецелесообразно.

Не создавать формальные type guards, которые всегда возвращают `true` или не проверяют заявленные условия.

### 4.3. Именование типов

- Использовать названия, отражающие назначение типа
- Не создавать слишком общие имена, например `Data`, `Result`, `Options`, без необходимого контекста
- Избегать совпадений с именами встроенных типов TypeScript, например `ReturnType`
- Сохранять принятые в проекте соглашения по размещению и экспорту типов

## 5. Выражения, переменные и условия

### 5.1. Промежуточные переменные

Сложные выражения разбивать на именованные промежуточные результаты.

Особенно это касается:

- Вложенных вызовов функций
- Цепочек логических операторов
- Сложных тернарных выражений
- Вычислений внутри объектов и массивов
- Вычисляемых ключей при обращении к объектам
- Выражений, выполняющих несколько логических действий

**Нежелательно:**

```ts
const preview = previews[getPreviewKey(effect.id, text.id)];
```

**Предпочтительно:**

```ts
const previewKey = getPreviewKey({
  effectId: effect.id,
  textId: text.id,
});

const preview = previews[previewKey];
```

Простые выражения оставлять без изменений.

```ts
const isVisible = effect.visible ?? true;
```

**Avoid unnecessary placeholder states.** Determine the final result directly when clearer instead of assigning a value only to overwrite it. Keep meaningful intermediate variables, genuine defaults and staged updates; a simple ternary is often clearer than a longer branch block.

### 5.2. Объекты

Если объект содержит больше одного свойства, записывать его в несколько строк.

```ts
const options = {
  volume: 1,
  loop: false,
};
```

Сложные вложенные объекты предварительно формировать в отдельных переменных.

**Нежелательно:**

```ts
setResolved({
  pathsKey,
  project,
  media: {
    images,
    videos,
  },
});
```

**Предпочтительно:**

```ts
const resolvedMedia = {
  images,
  videos,
};

setResolved({
  pathsKey,
  project,
  media: resolvedMedia,
});
```

Простые вложенные структуры допустимо оставлять внутри объекта, если их выделение не улучшает читаемость.

Не создавать сложные вложенные структуры непосредственно внутри `return` или аргументов функций, когда промежуточные переменные делают код понятнее.

### 5.3. Деструктуризация

Если при деструктуризации объекта или массива получается больше трёх элементов, размещать каждый элемент на отдельной строке.

**Неправильно:**

```ts
const { component, images = [], videos = [], ...options } = effect.options;
```

**Правильно:**

```ts
const {
  component,
  images = [],
  videos = [],
  ...options
} = effect.options;
```

При наличии `...spread` также предпочитать многострочную запись, если это улучшает восприятие.

### 5.4. Условия

Если условие содержит больше двух сравнений, переносить проверки на отдельные строки.

```ts
if (
  resolved?.pathsKey !== pathsKey
  || resolved.project !== project
  || resolved.name !== name
) {
  return null;
}
```

Сложные условия разбивать на именованные булевы переменные.

```ts
const hasValidPath = resolved?.pathsKey === pathsKey;
const hasValidProject = resolved?.project === project;
const hasValidName = resolved?.name === name;

if (!hasValidPath || !hasValidProject || !hasValidName) {
  return null;
}
```

Выбирать вариант, который проще читать в конкретной ситуации.

**Separate feature eligibility from missing data.** Express whether an operation should run or a component should mount at that decision point, rather than only replacing available data with a missing value. Prefer a direct guard when it clarifies intent, while preserving lazy evaluation and required hook calls.

Дополнительные требования:

- Избегать вложенных тернарных операторов
- Для сложных ветвлений использовать `if` / `else`
- Предпочитать ранние выходы `return`, `continue`, `throw`
- Не объединять независимые проверки в одно большое выражение без необходимости
- Не разбивать очевидные короткие условия исключительно ради соблюдения формального правила

### 5.5. Логические операторы

Не использовать `&&` для получения условного значения, если это может привести к нежелательному результату.

Например:

```ts
const preview = key && previews[key];
```

Это выражение может вернуть пустую строку вместо `undefined`.

Предпочитать явное выражение результата:

```ts
const preview = key ? previews[key] : undefined;
```

**Keep fallback chains semantically coherent.** Use short fallback chains with an obvious priority for the same value. Establish branch-specific choices separately instead of injecting `undefined` into a chain. Preserve the meanings of `false`, `0`, `''`, `null` and `undefined`; do not interchange `??` and `||` without checking their semantics.

**Resolve related optional values together.** When several calculations depend on one optional object, consider resolving them under one presence check instead of creating absent keys and temporary values. Keep simple optional chaining and nullish expressions when they are clearer.

### 5.6. Строки

Для объединения строк преимущественно использовать шаблонные литералы.

```ts
const message = `Недопустимый путь: ${relativePath}`;
```

Оператор `+` допустим, если он заметно улучшает читаемость, например при разделении очень длинной строки.

## 6. Функции

### 6.1. Аргументы функций

Для собственных функций с **тремя и более позиционными аргументами** по умолчанию использовать один объект-параметр.

**Нежелательно:**

```ts
getPreviewKey(effectId, itemId, key);
```

**Предпочтительно:**

```ts
getPreviewKey({
  effectId,
  itemId,
  key,
});
```

Деструктуризацию можно выполнять непосредственно в параметрах функции.

```ts
const getPreviewKey = ({
  effectId,
  itemId,
}: GetPreviewKeyParams) => {
  return `${effectId}:${itemId}`;
};
```

Дополнительные требования:

- Для сложных параметров предпочитать отдельный именованный тип
- Не применять правило к стандартным API и библиотечным функциям
- Не изменять установленные сигнатуры колбэков и обработчиков событий
- Не изменять публичные контракты без проверки всех мест использования
- Если позиционные аргументы необходимы для совместимости или предусмотрены существующим интерфейсом, сохранять контракт

### 6.2. Декомпозиция функций

Большие функции разбивать на логически самостоятельные операции.

Выносить в отдельные функции:

- Сложные преобразования данных
- Нормализацию значений
- Повторяющиеся вычисления
- Подготовку конфигураций
- Независимые проверки
- Повторяющуюся бизнес-логику

Не дробить небольшие функции на множество дополнительных вызовов без практической пользы.

### 6.3. Возвращаемые значения

В многострочных функциях отделять итоговый `return` пустой строкой от предшествующих операций.

```ts
const getFullName = (user: User) => {
  const firstName = user.firstName.trim();
  const lastName = user.lastName.trim();

  return `${firstName} ${lastName}`;
};
```

Не создавать дополнительные переменные исключительно ради оформления `return`.

Сложные выражения внутри `return` предварительно упрощать, когда это улучшает читаемость.

## 7. React и JSX

### 7.1. Общие принципы

Компоненты должны преимущественно отвечать за:

- Получение необходимых данных
- Подготовку данных для отображения
- Обработку пользовательских событий
- Рендеринг интерфейса

Сложную независимую логику выносить за пределы компонентов.

Не перегружать JSX вычислениями и преобразованиями данных.

**Respect API boundaries and React lifecycle.** Represent absence according to the receiving contract: domain data, controlled input, CSS, component or hook. Keep valid `null`/`undefined` inputs and controlled empty strings. Do not change mounting, state, hook order or side effects for cosmetic simplification; follow the Rules of Hooks and prevent numeric visibility guards from accidentally rendering zero.

### 7.2. Вычисления перед JSX

Вычислять производные значения, подписи, описания и другую логику отображения перед `return`.

**Нежелательно:**

```tsx
<button>
  {isProjectBusy ? 'Подождите...' : 'Сохранить'}
</button>
```

**Предпочтительно:**

```tsx
const projectBusyStatusLabel = isProjectBusy
  ? 'Подождите...'
  : 'Сохранить';

return (
  <button>
    {projectBusyStatusLabel}
  </button>
);
```

Простые значения можно использовать непосредственно в JSX.

Не создавать промежуточные переменные для очевидных обращений к уже подготовленным данным.

### 7.3. Деструктуризация перед JSX

Если в JSX используется больше двух свойств одного объекта, предпочитать предварительную деструктуризацию.

```tsx
components.map((componentCur) => {
  const {
    id,
    description,
    packageName,
    name,
    title,
  } = componentCur;

  return (
    <button
      key={id}
      type="button"
      title={description}
      onClick={() => onInsertCustomComponent(packageName, name)}
    >
      Добавить {title}
    </button>
  );
});
```

Если используется не больше двух свойств, деструктуризация необязательна.

Не выполнять избыточную деструктуризацию, если она ухудшает понимание кода.

### 7.4. Обработчики событий

Объявлять многострочные или сложные обработчики отдельно перед JSX.

**Неправильно:**

```jsx
onDelete={(name) => {
  setProperty(name, undefined);
  commitStyle();
}}
```

**Правильно:**

```tsx
const handleDelete = (name: string) => {
  setProperty(name, undefined);
  commitStyle();
};

return (
  <Properties
    onDelete={handleDelete}
  />
);
```

Если обработчик уже имеет подходящую сигнатуру, передавать его напрямую.

```tsx
onDelete={handleDelete}
```

Не создавать промежуточную стрелочную функцию без необходимости.

Короткие однострочные обработчики допустимы, если они остаются понятными и не содержат сложной логики.

### 7.5. Расположение обработчиков в пропсах

Пропсы обработчиков событий (`onClick`, `onChange`, `onFocus` и другие) размещать в конце списка.

Если обработчиков больше двух, отделять их от остальных пропсов пустой строкой.

Правило распространяется на:

- JSX-пропсы
- Деструктуризацию пропсов
- Типы и интерфейсы пропсов

```tsx
export const Images = ({
  images,
  canImport,

  onChange,
  onImportAsset,
  onDelete,
}: BackgroundImagesProps) => {
  // ...
};
```

### 7.6. Форматирование JSX

Если элемент содержит `children`, открывающий тег, содержимое и закрывающий тег располагать на отдельных строках.

**Неправильно:**

```tsx
<span>Название эффекта</span>
```

**Правильно:**

```tsx
<span>
  Название эффекта
</span>
```

Исключения допустимы, если переносы могут нарушить пробелы или отображение смешанного текстового содержимого.

Соседние JSX-элементы предпочтительно отделять пустой строкой.

Это относится и к ситуациям, когда однострочный элемент соседствует с многострочным.

Не вставлять пустые строки механически, если элементы образуют единую тесно связанную конструкцию и разделение ухудшает читаемость.

### 7.7. Условный рендеринг

Не использовать однострочные конструкции с `&&` для рендеринга компонентов.

**Нежелательно:**

```tsx
{showBackgrounds && <BackgroundInstances project={project} />}
```

**Правильно:**

```tsx
{showBackgrounds && (
  <BackgroundInstances project={project} />
)}
```

Сложные условия вычислять перед `return`.

Учитывать, что числовые и строковые значения в условиях React могут приводить к неожиданному отображению.

### 7.8. Зависимости React-хуков

В массивах зависимостей сначала указывать значения данных, затем функции.

```ts
useEffect(() => {
  updatePreview();
}, [effectId, options, updatePreview]);
```

Не удалять необходимые зависимости ради устранения предупреждений ESLint.

Не изменять семантику эффектов при перестановке или рефакторинге зависимостей.

### 7.9. Ref

Проект использует React 19.

- Не использовать `forwardRef` в новом коде
- Передавать `ref` как обычный prop
- При рефакторинге существующих компонентов использовать механизм React 19
- Проверять корректность типизации и передачи `ref`

Если код должен быть совместим с React 18, учитывать особенности старой модели передачи `ref` и не удалять `forwardRef` механически.

## 8. CSS и classnames

Для объединения и условного применения CSS-классов использовать исключительно библиотеку `classnames`.

Не использовать для формирования `className`:

- Тернарные операторы
- Конкатенацию строк
- Шаблонные литералы
- Массивы с `.join()`
- Самостоятельные функции объединения классов

**Неправильно:**

```tsx
className={colorDisabledReason ? styles.DisabledColors : styles.Colors}
```

```tsx
className={`${styles.Select} ${layoutStyles.Unit}`}
```

```ts
const classes = [styles.Button, variantClass, className]
  .filter(Boolean)
  .join(' ');
```

**Правильно:**

```ts
const editorScreenClassNames = classNames({
  [styles.EditorScreen]: true,
  [styles.isStructureVisible]: showStructure,
  [styles.isNarrativeHidden]: !showNarrative,
});
```

Одиночный статический класс передавать напрямую.

```tsx
className={styles.Button}
```

Не создавать промежуточные переменные для одиночного статического класса без необходимости.

## 9. Структура проекта и декомпозиция

### 9.1. Организация компонентов

**Один React-компонент — одна директория.**

- Каждый компонент размещать в отдельной директории
- Использовать `index.ts` для публичного экспорта
- Не размещать несколько самостоятельных компонентов в одном файле
- Использовать существующие соглашения об именовании файлов и директорий
- Не объединять независимые компоненты исключительно ради уменьшения количества файлов

Исключения из этого правила допускаются только по явному согласованию.

### 9.2. Разделение ответственности

Выносить сложную логику из компонентов в соответствующие модули.

Для организации использовать при необходимости:

- `components/` — вложенные компоненты
- `hooks/` — React-хуки
- `utils/` — вспомогательные функции
- `@types.ts` — связанные типы
- `index.ts` — публичные экспорты

Чистые функции, не зависящие от React, предпочтительно размещать в `utils`.

Повторяющуюся логику React выносить в собственные хуки.

Использовать `index.ts` для формирования понятного публичного интерфейса модуля.

### 9.3. Размер модулей

Если файл становится слишком большим или объединяет несколько разных обязанностей, разделять его на логические части.

Не создавать дополнительные уровни вложенности без необходимости.

Ориентироваться на:

- Ответственность модуля
- Повторное использование
- Удобство навигации
- Простоту тестирования
- Читаемость

Не дробить небольшие функции на множество файлов без практической пользы.

## 10. Тексты пользовательского интерфейса

Эти правила относятся к текстам, которые видит пользователь ActiveBook.

### 10.1. Обращение к пользователю

Использовать вежливое обращение на «Вы».

Не переходить на «ты» в интерфейсных сообщениях.

### 10.2. Пунктуация

Не ставить точку в конце последнего или единственного предложения интерфейсного текста.

**Нежелательно:**

```ts
const message = 'Проект успешно сохранён.';
```

**Правильно:**

```ts
const message = 'Проект успешно сохранён';
```

Если текст состоит из нескольких предложений, сохранять необходимые знаки препинания между ними.

Вопросительные, восклицательные знаки и другие смысловые знаки пунктуации сохранять.

### 10.3. Кавычки

В русскоязычных текстах интерфейса использовать кавычки-лапки `"..."`, а не кавычки-ёлочки `«...»`.

Правило не относится к синтаксису строк TypeScript, JSON и другим техническим конструкциям.

### 10.4. Область применения

Правила интерфейсной пунктуации и обращения не распространяются автоматически на:

- Документацию
- Комментарии в коде
- Технические сообщения консоли
- Тексты исключений
- Внешние данные

В этих случаях использовать оформление, соответствующее контексту.

## 11. Безопасность рефакторинга

**Рефакторинг не должен изменять поведение программы.**

При любых преобразованиях обязательно:

- Сохранять исходные условия и порядок выполнения операций
- Учитывать короткое замыкание логических операторов
- Сохранять поведение при `null`, `undefined`, `false`, `0` и пустых строках
- Не изменять возвращаемые значения и типы без необходимости
- Не добавлять лишние вычисления или побочные эффекты
- Сохранять порядок асинхронных операций
- Не изменять контракты функций без проверки всех мест использования
- Проверять импорты и экспорты при переносе модулей
- Не изменять несвязанный с задачей код

### 11.1. Проверки после изменений

После рефакторинга:

- Проверять TypeScript
- Запускать ESLint
- Запускать существующие тесты, относящиеся к изменённой логике
- При изменении нетривиального поведения добавлять регрессионные тесты, если это целесообразно
- Проверять места использования изменённых функций, типов и компонентов

Не утверждать, что код проверен, если соответствующая проверка фактически не выполнялась.

### 11.2. Сомнения в эквивалентности

Если нет уверенности, что преобразование сохраняет поведение:

- Не выполнять рискованный рефакторинг механически
- Сначала установить исходную семантику
- По возможности подтвердить её тестом
- При невозможности подтвердить безопасность сохранить исходную реализацию
- Сообщить о выявленной неопределённости

## 12. Итоговый принцип

**Одна операция — одна понятная мысль.**

Код должен читаться последовательно, без необходимости мысленно разбирать сложные вложенные выражения.

При этом количество строк, переменных, функций и файлов не является самостоятельным показателем качества.

Цель правил — сделать код понятным, поддерживаемым и предсказуемым, сохраняя его корректность и существующее поведение.
