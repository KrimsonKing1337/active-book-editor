# ContentValidation: issue #65

Проверка [issue #65](https://github.com/KrimsonKing1337/active-book-editor/issues/65)
выполнена поверх `e1b2f4291ca315f0eca9dcdce8eb4790663de6fb` в существующей
ветке `codex/editable-carousel`. Один Editor и исходная модель JSON сохранены.

## Причины и исправления

Раньше `insertContentAt` определял контекст только по началу диапазона. При
выделении от обычного параграфа до середины слайда проверка разрешала карусель
как вставку в основной нарратив. Обычный текст и блоки также проходили через
границы контейнеров. После fitting получался уже валидный JSON, поэтому проверка
готовой транзакции не могла восстановить исходное намерение и обнаружить потерю
границ. В первоначальной матрице 8 операций ошибочно принимались; ещё 7
отклонялись по типу входных данных, а не по пересечению границ.

`validateRange` проверяет оба конца фактического диапазона в текущем `tr.doc`.
Команды, DOM paste и `EditorView.pasteHTML` отклоняют недопустимый диапазон до
вызова методов fitting. Для drop проверяется точка указателя; для внутреннего
переноса дополнительно проверяется удаляемое выделение до `deleteSelection`.

| Сценарий | Поведение |
| --- | --- |
| Оба конца в одном слайде | Обычный текст и блоки разрешены |
| Выделение содержит карусель целиком, концы снаружи | Замена разрешена, включая новую карусель |
| Начало снаружи, конец в слайде или наоборот | Отклонение любого входного содержимого |
| Концы в разных слайдах | Отклонение любого входного содержимого |
| Вставка между слайдами | Отклонение до поиска другой подходящей позиции |
| Карусель/segment внутри слайда | Отклонение исходного HTML/JSON до fitting |
| Внешний drop при произвольном выделении | Вставка по указателю; выделение не удаляется |
| Внутренний move | Проверка исходного выделения и точки назначения |

В пределах одного слайда действует штатное поведение ProseMirror для соединения
параграфов при вставке в середину текста. При замене целого параграфа сохраняются
типы вставленных блоков и marks. Undo/redo проверяет точный исходный JSON.

Отдельно воспроизведена проблема штатных clipboard/drag `Slice`: открытые
обёртки `carousel`/`carouselSlide` являются контекстом скопированного текста,
а не новой авторской каруселью. `clipboardGuards` учитывает только известный
открытый контекст для проверки, передавая оригинальный Slice ProseMirror без
изменений. Закрытая карусель остаётся полноценным контейнером. HTML с открытым
`carouselSlide` и `data-pm-slice` принимается только clipboard-путём; команды
импорта документа по-прежнему отвергают такой одиночный слайд. Поддельные
метаданные не разрешают вложенные carousel/segment.

## Измерения

Среда: Linux x86_64, Node 24.19.0, Vitest 4.1.12, headless Chromium 154,
`navigator.hardwareConcurrency = 3`. Использован локальный Core 0.0.63.
Оба варианта измерены одним benchmark на одной машине.

Каждая страница содержит 1000, 5000 или 10000 обычных параграфов и дополнительно
10 каруселей, по 2 слайда и 10 параграфов на слайд. В параграфах два текстовых
узла, один с bold. Размеры JSON: 508617, 2204777 и 4324797 байт.

На каждой странице выполняются:

- 6 символов прогрева и затем 100 настоящих нажатий клавиш внутри первого слайда;
- 20 DOM paste событий, каждое с тремя HTML-блоками;
- 10 полных замен документа через `setContent`, меняющих текст каждого блока.

Измеряется время существующего `filterTransaction` и синхронного `view.dispatch`,
включающего этот фильтр. Последнее не является полной задержкой пользовательского
ввода: сюда не входят IPC Playwright, предварительный разбор JSON/HTML команды
и последующая асинхронная отрисовка React. Проверяется число реальных транзакций
каждого сценария. Значения округлены до 0,1 мс; это наблюдения, а не CI-порог.

| Параграфов | Сценарий | Проверка до, p50 / p95 (мс) | После, p50 / p95 (мс) | Dispatch p50 до / после (мс) |
| ---: | --- | ---: | ---: | ---: |
| 1000 | Ввод | 0.6 / 1.5 | 0.1 / 0.2 | 1.7 / 1.2 |
| 1000 | Paste | 1.1 / 2.1 | 0.1 / 1.4 | 5.4 / 5.0 |
| 1000 | Полная замена | 1.9 / 7.5 | 1.5 / 5.9 | 17.8 / 17.8 |
| 5000 | Ввод | 2.5 / 3.8 | 0.3 / 0.4 | 5.4 / 3.0 |
| 5000 | Paste | 2.3 / 5.2 | 0.2 / 0.3 | 9.8 / 13.0 |
| 5000 | Полная замена | 2.0 / 2.4 | 2.4 / 7.9 | 110.4 / 111.6 |
| 10000 | Ввод | 4.5 / 7.5 | 0.4 / 0.6 | 9.5 / 4.4 |
| 10000 | Paste | 4.0 / 6.3 | 0.3 / 0.4 | 24.2 / 17.8 |
| 10000 | Полная замена | 3.7 / 4.4 | 4.4 / 7.6 | 380.1 / 241.3 |

Ускорение относится к самому фильтру при локальном вводе и paste. Полная замена
не стала дешевле: в большом случае медиана проверки выросла с 3,7 до 4,4 мс.
Полная проверка сохранена намеренно; её стоимость мала относительно обновления
всего DOM. Общий dispatch также не улучшается во всех случаях: для paste на
5000 параграфов медиана выросла с 9,8 до 13,0 мс при снижении стоимости фильтра.
По одному прогону и 10 большим заменам нельзя приписывать все отличия DOM/GC
только валидатору; сырые результаты приведены без выборочного исключения случаев.

До исправления в случае 10000 параграфов проверка занимала около 52% суммарного
времени dispatch при вводе. Это подтвердило необходимость локальной оптимизации.

`createDocumentValidator` хранит WeakSet только полностью проверенных документов.
В качестве базы сравнения используется `state.doc` текущей транзакции, только
если он уже прошёл проверку. Стандартные `Fragment.findDiffStart/findDiffEnd`
ProseMirror определяют изменённый диапазон; проверяются все пересечённые им
верхние блоки. Неизменённые фрагменты не сериализуются заново. Настоящий родитель
по-прежнему проверяется схемой; изменённые блоки проходят `Node.check()` и прежний
общий JSON-валидатор в проекции того же ProseMirror-документа. При ошибке полная
проверка восстанавливает исходный путь диагностики. Отклонённые по содержимому
документы не становятся доверенной базой сравнения.

Холодная база и полная замена сохраняют полную проверку. Изменённая карусель
целиком проверяется со своими слайдами; это не кеш каждого текстового листа.
Поиск различий и проверка контекста остаются линейными в худшем случае.
Отдельного AST, JSON-кеша, сильной ссылки на прошлую страницу и изменений
book-builder не добавлено. Проверка нескольких больших полных замен также
выявила ненужные расходы при кешировании идентичности каждого блока: итоговый
вариант отмечает только один корневой документ на принятую транзакцию.

Повторить измерение:

```bash
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run bench:content
```

Если Playwright использует собственный Chromium, переменная не нужна. Результат:
`test-results/content-validation-benchmark.json`, поле
`testResults[].assertionResults[].meta.contentValidation`. Benchmark включается
только через `npm run bench:content`; обычный browser-прогон пропускает его.
Сырые сравниваемые измерения сохранены в
[benchmarks/issue65-content-validation.json](./benchmarks/issue65-content-validation.json).

## Регрессионные проверки

Unit-тесты проверяют границы диапазонов, переиспользование неизменённых блоков,
повторное отклонение неизвестных узлов, heading attrs и небезопасных marks,
вложенную карусель, пустой документ и неправильный корневой контекст при тёплом
кеше. Путь ошибки остаётся путём исходного, а не сокращённого документа.

Браузерная матрица охватывает три пересечения диапазона и текст/несколько
блоков/HTML carousel/JSON carousel/segment там, где формат поддерживается API.
Настоящие ClipboardEvent/DragEvent и HTML штатного сериализатора проверяют
копирование и перенос нескольких блоков. Отрицательные тесты проверяют отсутствие
вызовов fitting, сохранение документа и истории. Для допустимых замен и переносов
undo/redo восстанавливает точный документ. JSON не декодируется из произвольного
`text/plain` clipboard: структурный JSON поступает через TipTap-команды.

Исходные проверки: TS и 94 unit-теста прошли; полный browser-прогон дал 29 pass
и 1 существующий screenshot failure. ESLint: 70 errors / 47 warnings.

Итоговые проверки:

- TypeScript приложения и тестов — pass; 105 unit-тестов — pass.
- Полный browser-прогон: 81 pass, 1 прежний screenshot failure и 1 намеренно
  пропущенный opt-in benchmark. Все 52 новых браузерных регрессии проходят.
- Production book build/read — pass, включая мышь/клавиатуру/touch и проверки
  отсутствия console/page errors. Сохраняется предупреждение о размере chunk.
- Stylelint — pass. ESLint — те же 70 errors, новых ошибок нет; 48 warnings,
  дополнительное предупреждение относится к длине файла матричных тестов.

Screenshot failure — `effects-composition`: 1116 отличающихся пикселей в тексте.
Он воспроизведён на точном исходном `e1b2f42` с теми же зависимостями и Chromium
в отдельном снимке исходников; для него разрешён доступ Vite к общим установленным
зависимостям. Там же воспроизводятся сообщения старой fixture об отсутствующих
`range-pattern.svg` и `movie.webm`. Эталон и несвязанные ошибки не изменены.
